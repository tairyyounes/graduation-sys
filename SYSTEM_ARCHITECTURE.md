# ProposalGuard AI — Graduation Management System
## Comprehensive Technical Report

---

## 1. What Is This System?

**ProposalGuard AI** is a web-based **Graduation Project Management System** built for a college (College of Computer Technology – Tripoli, Libya). Its primary purpose is to manage the full lifecycle of student graduation project proposals — from a student writing a draft idea, through department review and approval, to the final decision.

The system has **three types of users**, each with a completely separate dashboard and set of permissions:

| Role | What they do |
|------|-------------|
| **Admin** | Manages all users and departments system-wide |
| **Department Member** | Reviews student proposals, manages students in their department |
| **Student** | Creates, submits, and tracks their graduation proposals |

## 3. Database Schema

There are **8 database tables** in total. Here is each one explained:

### `departments`
Stores the academic departments (e.g., Programming, Networks, Control).
- `department_id` — Primary key
- `department_name` — Unique name

### `users`
The main authentication table. Every person who can log in is a user.
- `id` — Primary key
- `full_name` — User's display name
- `email` — Unique login email
- `password` — Hashed (bcrypt)
- `role` — One of: `admin`, `student`, `department_member`
- `department_id` — FK to `departments` (nullable, only for students & dept members)
- `is_active` — Boolean, can disable a user without deleting them

### `students`
An extended profile for users who are students. Linked by email.
- `student_id` — Primary key
- `student_number` — Unique registration number
- `full_name`, `official_email`
- `department_id` — FK to `departments`
- `semester` — Currently enforced to be 8 (a business rule: only 8th semester students can register)
- `is_active` — Active status

> **Note:** A student has BOTH a `users` row (for login) AND a `students` row (for academic profile). They are linked via `email = official_email`.

### `proposals`
Represents a graduation project proposal.
- `proposal_id` — Primary key
- `department_id` — Which department it belongs to
- `submission_status` — `draft` | `submitted` | `archived`
- `review_status` — `pending` | `under_review` | `revision_requested` | `accepted` | `rejected`
- `is_locked` — Boolean (locked proposals can't be edited)

### `project_members`
Links students to proposals (teams of up to 3 students).
- `proposal_id` — FK to `proposals`
- `student_id` — FK to `students`
- `member_role` — `owner` | `member`
- `invitation_status` — `pending` | `accepted` | `rejected`
- `joined_at` — Timestamp
- **Unique constraint**: One student can't be in the same proposal twice

### `proposal_versions`
Every saved version of a proposal's content.
- `version_id` — Primary key
- `proposal_id` — FK to `proposals`
- `version_number` — Integer version counter
- `title`, `problem`, `solution`, `functions`, `objectives`, `tags`, `technologies_used`
- **Unique constraint**: (proposal_id, version_number) pair is unique

### `decisions`
Records a reviewer's decision on a specific proposal version.
- `decision_id` — Primary key
- `proposal_id` — FK to `proposals`
- `version_id` — FK to `proposal_versions`
- `reviewer_id` — FK to `users` (the dept member who decided)
- `decision_type` — `accepted` | `rejected` | `revision_requested`
- `decision_note` — Optional text note from the reviewer
- `decision_date` — Timestamp

### `activity_log` (Spatie package table)
Auto-generated by the Spatie Activitylog package.
- Logs who did what, to which model, and when
- Tracks Eloquent model events: `created`, `updated`, `deleted`
- Has custom description support for manual log entries

## 4. Backend Architecture

### 4.1 Authentication (`routes/auth.php` + Laravel Breeze)
The standard Laravel Breeze authentication system provides:
- `GET /login` — Login form
- `POST /login` — Process login → redirects to `/dashboard`
- `POST /logout` — Log out
- `GET /register` — Registration form
- `POST /register` — Create new account
- Password reset and email verification flows

### 4.2 Role-Based Access Control (RBAC)

The system uses a **custom `RoleMiddleware`** (`app/Http/Middleware/RoleMiddleware.php`):

```php
public function handle(Request $request, Closure $next, string $role): Response
{
    if (!auth()->check()) {
        return redirect('/login');
    }
    if (auth()->user()->role !== $role) {
        abort(403, 'Unauthorized');
    }
    return $next($request);
}
```

It works as a route guard: `middleware('role:admin')` on a route means only users whose `role` column equals `'admin'` can access it. Everyone else gets a 403 Forbidden error.

### 4.3 The Dashboard Router (`routes/web.php`)

When a logged-in user visits `/dashboard`, they are automatically redirected based on their role:

```
/dashboard  →  admin → /admin/dashboard
            →  department_member → /department/dashboard
            →  student → /student/dashboard
```

All three dashboard routes are protected by `middleware('auth')` and the appropriate `role:xxx` guard.

### 4.4 API Endpoints

All API routes return JSON and require authentication. Here is the complete list:

**Admin: User Management** (`/admin/users`) — guarded by `role:admin`
| Method | URL | What it does |
|--------|-----|-------------|
| GET | `/admin/users` | List all users + departments |
| POST | `/admin/users` | Create a new user |
| PUT | `/admin/users/{user}` | Update a user |
| DELETE | `/admin/users/{user}` | Delete a user |

**Admin: Department Management** (`/admin/departments`) — guarded by `role:admin`
| Method | URL | What it does |
|--------|-----|-------------|
| GET | `/admin/departments` | List all departments with counts |
| POST | `/admin/departments` | Create a new department |
| GET | `/admin/departments/{id}` | Get one department's details, members, students |
| PUT | `/admin/departments/{id}` | Update a department's name |
| DELETE | `/admin/departments/{id}` | Delete a department |

**Admin: Activity Logs** — guarded by `role:admin`
| Method | URL | What it does |
|--------|-----|-------------|
| GET | `/admin/activity-logs` | Paginated list of all system events (50 per page) |

**Department: Student Management** (`/department/students`) — guarded by `role:department_member`
| Method | URL | What it does |
|--------|-----|-------------|
| GET | `/department/students` | List all students in this dept (up to 200) |
| POST | `/department/students` | Manually add one student |
| POST | `/department/students/import` | Bulk import students via CSV file |

## 5. Backend Controllers — Detailed Breakdown

### `UserManagementController` (Admin)
This is the most complex backend controller. Here is what each action does in detail:

**`index()`** — Lists all users, joining with `departments` and `students` tables so that each user record also shows their department name and student number (if applicable).

**`store()`** — Creates a new user with full validation:
- Requires `full_name`, `email`, `role`, `password`
- For students and department members: also requires `department_id`
- For students: also requires a unique `student_number`
- If the new user is a student, it also creates a matching row in the `students` table in the **same database transaction** — if either insert fails, both are rolled back
- Default password for manually created students: the password they set

**`update()`** — Updates an existing user:
- If they change from another role to `student`, it creates a `students` record
- If they change from `student` to another role, it **deletes** their `students` record
- Email changes are propagated to the `students` table
- Password is only updated if a new one is provided

**`destroy()`** — Deletes a user:
- If they're a student, also deletes their `students` row
- All in a transaction

### `DepartmentController` (Admin)
- **`index()`**: Returns all departments with counts of department members, students, and a placeholder `0` for proposals (proposals not yet integrated)
- **`show()`**: Returns one department's full details: its members, its students, and placeholders for proposals
- **`store()`**, **`update()`**, **`destroy()`**: Basic CRUD with activity logging

### `ActivityLogController` (Admin)
- **`index()`**: Fetches paginated Spatie activity logs, eager-loading the causer (user who did the action) to avoid N+1 queries. Formats for frontend: time, actor name, action description, target name.

### `StudentImportController` (Department)
The most detailed controller. Handles adding students to a department.

**`store()`** — Manually add one student:
- Validates: student number (unique), name, email (unique), semester must be exactly 8
- Creates a `students` row
- Also creates a `users` row so the student can log in. **Default password = student number**
- Uses `insertOrIgnore` on users to avoid crash if user already exists

**`import()`** — Bulk CSV import:
1. Validates the uploaded file is `.csv` or `.txt`, max 2MB
2. Reads the CSV header row and normalizes column names to lowercase
3. Checks that required columns exist: `student_number`, `full_name`, `official_email`, `semester`
4. Reads every row, validates each one individually. **If any row fails, the entire import is rejected**
5. Batch-inserts all students at once with `insertOrIgnore` (skips duplicates)
6. Batch-creates user accounts with default password = student number
7. Logs the import action

## 6. Frontend Architecture

The frontend is a **hybrid architecture** — not a pure SPA, not purely server-rendered. Each dashboard is its own independent Vue application mounted inside a Blade template.

### 6.1 Entry Points

| File | What it mounts |
|------|----------------|
| `resources/js/app.js` | General app bootstrap |
| `resources/js/admin-dashboard.js` | Mounts `AdminDashboard.vue` + admin Vue Router |
| `resources/js/department-dashboard.js` | Mounts `DepartmentDashboard.vue` + department Vue Router |
| Student dashboard | Mounted via `student-dashboard.js` or `app.js` on the student Blade template |

### 6.2 How Routing Works

**Admin and Department dashboards** use **Vue Router** (`vue-router`). When the user navigates inside the dashboard, the URL changes and Vue Router swaps the displayed component — without a full page reload. This is a true SPA inside the dashboard.

**Student dashboard** uses a simpler approach: a single `currentView` ref, and `v-if` / `v-else-if` directives to show/hide sections. No Vue Router — navigation doesn't change the URL.

### 6.3 Admin Router (`resources/js/router/admin.js`)
```
/admin/dashboard          → AdminOverviewSection.vue
/admin/dashboard/users    → AdminUsersSection.vue
/admin/dashboard/departments         → AdminDepartmentsSection.vue
/admin/dashboard/departments/:id     → AdminDepartmentDetailsSection.vue
/admin/dashboard/activity  → AdminActivitySection.vue
/admin/dashboard/*         → redirects to /admin/dashboard
```

### 6.4 Department Router (`resources/js/router/department.js`)
```
/department/dashboard           → DepartmentOverviewSection.vue
/department/dashboard/queue     → DepartmentQueueSection.vue
/department/dashboard/proposal  → DepartmentProposalSection.vue
/department/dashboard/decisions → DepartmentDecisionsSection.vue
/department/dashboard/students  → DepartmentStudentsSection.vue
/department/dashboard/*         → redirects to /department/dashboard
```

### 6.5 Shared Layout Component (`AppDashboardLayout.vue`)
Both `AdminDashboard.vue` and `DepartmentDashboard.vue` use this shared layout. It provides:
- A **white sidebar** with the ProposalGuard AI brand, navigation links (using `<router-link>`), and user info at the bottom
- A **main content area** with `<router-view>` wrapped in a CSS fade transition
- A **mobile sidebar overlay** that slides in when a hamburger button is tapped
- A **slot** called `footerActions` for custom buttons (Admin uses this for a language toggle)

The layout accepts props: `navItems`, `brandTitle`, `brandSubtitle`, `navTitle`, `user`.

## 8. Data Flow — End to End Example

### Example: Admin Creates a Student User

```
1. Admin clicks "Add User" in AdminUsersSection.vue
2. AdminUserModal.vue opens
3. Admin fills in: name, email, role=student, department, student_number, password
4. Admin clicks "Submit"
5. AdminUsersSection.submitUserForm() runs:
   - Builds payload
   - Sends POST /admin/users with JSON + CSRF token
6. Laravel routes to UserManagementController@store
7. Controller validates all fields
8. Opens DB transaction:
   a. Creates users row (hashed password)
   b. Creates students row (same email, student_number, semester=8)
9. Commits transaction
10. Returns JSON with the new user
11. Vue calls loadUsers() to refresh the table
12. Toast notification: "User created successfully."
```

### Example: Department Member Imports Students via CSV

```
1. Dept member clicks "Import CSV" in DepartmentStudentsSection.vue
2. File picker opens, they select a .csv file
3. Component sends POST /department/students/import (multipart form)
4. StudentImportController@import runs:
   a. Validates file is .csv and under 2MB
   b. Opens file, reads header row
   c. Checks required columns exist
   d. Reads each data row, validates row-by-row
   e. If any row fails → returns 422 error with row number
   f. Batch inserts all students via insertOrIgnore
   g. Batch creates user accounts (password = student_number)
   h. Logs the action to activity_log
5. Returns: { message, imported_count }
6. Vue shows toast with success message
7. Vue refreshes the student list
```

## 9. Security

| Mechanism | How it works |
|-----------|-------------|
| **Authentication** | Laravel session-based auth via Laravel Breeze |
| **CSRF Protection** | Every mutating request (POST/PUT/DELETE) requires a CSRF token from `<meta name="csrf-token">` |
| **Role Guard** | `RoleMiddleware` checks the `role` column on every protected route |
| **Password Hashing** | All passwords stored as bcrypt hashes — never plaintext |
| **Activity Logging** | All sensitive actions (create/update/delete user/department) are logged with who did it and when |
| **Input Validation** | All API inputs are validated server-side with Laravel's Validator. Frontend forms also show server validation errors. |
| **Transaction Safety** | Multi-table writes (e.g., creating user + student record) are wrapped in DB transactions — either both succeed or neither does |
